# 验收方法

> 本仓库的验收不是"跑一遍没报错"，而是**一组必须通过的断言 + 一组必须被抓住的错误**。

## 1. 黑盒原则

全部用例遵守三条：

1. **只走公开路径与公开接口** —— 不 `require` 内部模块，不读私有字段，不 mock 内部函数。
2. **不依赖白盒知识** —— 用例写的是"外部观察到什么"，不是"内部怎么实现"。
3. **失败必须可定位** —— 每条断言对应一个具体违约点，不是笼统的"should work"。

**为什么不用白盒测试**：白盒用例会暴露内部 API、阈值与期望行为，与"发布件不含明文设计"的目标冲突。更实际的原因是——白盒测试容易变成"测试自己写的实现"，而黑盒测试测的是"发布件对外的承诺"。

## 2. 用例分布

全套 **58 条**，按六个套件组织：

| 套件 | 用例 | 职责 | 是否随仓库提供 |
|---|---|---|---|
| `01_packaging` | 7 | 发布件形态与洁净度 | 是 |
| `02_brain_ab` | 9 | 仿生脑 A/B 安全链 | 否 |
| `03_motion_cd` | 14 | 运动脑 C/D 安全链与执行 | 否 |
| `04_bases` | 12 | 三底座判定正确性 | 否 |
| `05_centers` | 13 | 模型中心三层行为 | 否 |
| `06_python` | 3 | Python 字节码形态 | 否 |
| **合计** | **58** | | |

`02`–`06` 的用例代码本身描述了各条安全链的判定顺序与违约码语义，属于受控内容，**随评估包单独提供**，不在本仓库。本仓库保留 `01_packaging`，因为它的作用是"防自己"——证明发布件里确实没有明文源码、没有个人路径、ABI 自检可用，这三件事谁都可以复核。

## 3. `01_packaging` 的七条断言

```
10 个 dist 齐全且各自有 package.json
dist 内所有 .js 都是 bytenode 桩（体积小、无函数体、指向同名 .jsc）
dist 内没有 plaintext JS 源码（>400B 的 .js 视为泄露）
Python 一律 sourceless .pyc，且数量与 magic 符合 3.11.9
全仓（含二进制）不含未掩码的 Users 用户名路径与个人标识
仓库根文件与 .gitignore 关键项齐全
ABI 自检脚本退出码为 0
```

第 3 条值得单独说：**用体积阈值判定泄露**（`>400B` 的 `.js` 视为明文源码）。这条是防自己——构建脚本哪天把源码带进来了，验收会先红。

## 4. 其余五套的覆盖范围

不列具体断言，只说测什么：

| 套件 | 覆盖范围 |
|---|---|
| `02_brain_ab` | 仿生脑侧的安全门与生命支持：放行/拦截的判定边界、急停的锁存与恢复、看门狗超时后的通道行为、A 与 B 两个版本语义一致性 |
| `03_motion_cd` | 运动脑侧：急停与复位令牌、动作过滤的各类违约情形、Mock 后端与执行桥的串联、世界模型预测的维度与数值有效性 |
| `04_bases` | 三个底座：规格硬校验、证据原语的判定、控制器解析在缺证据时的降级结论（含负结果对照） |
| `05_centers` | 模型中心三层：契约层并排合成、运行层安全监督的完整生命周期、门面在缺证据时的降级上报 |

各套断言的具体阈值、违约码与期望值属于受控内容，需要时通过评估包获取。

## 5. 突变证伪

58 条用例全绿只说明"当前实现满足断言"。它不说明**断言本身有效**——一个永远为真的断言也会全绿。

所以发布流程里另有一组**突变证伪**：

```
对被测代码做一处语义突变（改坏）
   ├─▶ 指定用例必须转红      ← 证明这条断言真的在测这件事
   ├─▶ 同文件其余用例保持绿   ← 证明突变是局部的，没有污染
   └─▶ 恢复原文后 md5 与原文一致 ← 证明改动被干净回滚
```

发布记录中保留 **6 条**这样的证伪样本。突变副本（`repo_mut/`）不随包发布。

> 这一步的成本不高，但它是"验收可信"与"验收走流程"的分界线。

## 6. 完整性与 ABI

| 手段 | 覆盖 | 用途 |
|---|---|---|
| `sha256sums.txt` | 仓库内除自身与 `node_modules/`、`.git/` 外**每个文件** | 下载后逐文件校验 |
| `scripts/verify-abi.js` | Node / V8 版本、`.jsc` 可加载性 | 换环境后第一步自检 |
| `01_packaging` 用例 | 桩文件形态、明文泄露、用户名掩码 | 发布件洁净度 |

```bash
# 校验完整性
sha256sum -c sha256sums.txt

# ABI 自检（退出码 0 才可继续）
node scripts/verify-abi.js
```

## 7. 复现

```bash
npm install
node scripts/verify-abi.js
npm test                                                    # 7 条（发布件形态）
node acceptance/run-one.js acceptance/01_packaging.test.js  # 单组
```

## 8. 这套验收**不能**证明什么

诚实列出边界，避免被误读：

| 不能证明 | 原因 |
|---|---|
| 真机动作成功率 | 本发布不含权重与传输驱动，无法上真机 |
| 控制周期指标 | 验收测的是断言，不是性能基准 |
| 长期稳定性 | 没有 soak test / 长时间运行数据 |
| 与第三方本体的兼容性 | 只覆盖 7 台已注册 Profile |
| 安全性（形式化意义） | 只做了工程级安全门验证，不是形式化验证 |

**这五条不是待办清单，是这份验收的作用域声明。** 任何超出这五条的结论，都需要另外的证据。
